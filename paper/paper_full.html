Abstract—Managed function-as-a-service (FaaS) platforms concentrate the execution of customer code in provider-operated data centres, which raises cost, restricts data placement, and leaves participants' already-provisioned hardware idle. This paper presents Hypercore, a distributed runtime that executes user-supplied TypeScript functions on ordinary computers contributed by participants instead of on centralised compute. Hypercore separates responsibility into three planes: a control plane that stores function metadata and source; a message plane that routes work to nodes over one long-lived Server-Sent Events (SSE) connection per computer, eliminating message brokers, inbound port forwarding and distributed credentials; and an execution plane in which a desktop agent (Tauri 2, Rust) compiles TypeScript to JavaScript with esbuild, compiles the JavaScript to WebAssembly with Javy, and executes the resulting module inside the wasmtime sandbox under WASI. Invocations are relayed from the control plane to a selected node through that node's persistent stream and returned over a second HTTP callback. Termination of untrusted or buggy code is guaranteed by layered timeouts (the agent times out T−2000ms into a T+5000ms server wait), a 2×109instruction fuel budget, and Wasm epoch interruption. We formalise the system as interacting state machines, derive its event-delivery and reconnection behaviour (bounded exponential backoff with expected wait E[N]=(1−p)/pad attempts), analyse crash-consistency (in-flight calls are lost with probability 1−e−λcTa control-plane crash), develop naming and queueing models, and give a cost model with a closed-form break-even invocation volume. An evaluation plan with five research questions, workload, metrics and sample-size methodology is included; results are reported as they are collected. The architecture demonstrates that participant-owned, NAT-friendly serverless execution is practical when user code is confined to WebAssembly and the control plane never executes it.

Index Terms—WebAssembly, serverless computing, function-as-a-service, edge computing, distributed systems, server-sent events, sandboxing, firmware-free deployment, TypeScript.

I. Introduction

Function-as-a-service platforms such as AWS Lambda, Google Cloud Functions and Cloudflare Workers established a simple contract: the customer submits a function, and the provider executes it — somewhere. The simplicity conceals three structural costs. Cost: the provider runs elastic, dedicated capacity whose amortisation is priced per invocation, and customers are billed even for work their own idle machines could have performed. Placement: the provider, not the data owner, chooses where code runs, which matters for latency and for data-jurisdiction requirements. Closedness: participation in the execution fleet is reserved to the provider; a customer's workstation, home server or lab machine cannot contribute.

This paper presents Hypercore, a runtime built around the opposite premise: any computer can join the execution fleet, and a central control plane decides which computer runs which job. The control plane never executes user code. This preserves a cheap, single point of negotiation (accounts, naming, billing, liveness) while pushing risk, compute cost and capacity out to participant devices. Three engineering problems dominate the design space: executing untrusted code safely on someone else's expensive machine; routing work to machines that sit behind consumer routers and firewalls without configuration; and remaining honest about what a single-process control plane can and cannot guarantee durably. Hypercore resolves them with three commitments.

Safety through WebAssembly. A user function is never executed as native code, nor as JavaScript in a Node.js runtime. Each function is compiled in two steps — TypeScript to JavaScript with esbuild, then JavaScript to a self-contained Wasm module with Javy — and executed by the Rust wasmtime engine under WASI preview 1. The module's entire world is three inputs: standard input (the caller's HTTP body), three HTTP context variables in its environment, and a byte budget of output. There is no path to the filesystem, network or host memory outside the sandbox.

NAT-friendly transport. Every participating computer opens exactly one outbound, long-lived HTTP request and keeps it open; the control plane writes events into that response as work arrives (Server-Sent Events). Because nodes only make outbound connections, no router needs configuration, no inbound firewall rule exists, and the installer carries no broker credentials — the agent needs nothing but a web address to join.

Honest failure semantics. The system distinguishes a function that ran and failed (HTTP 502) from a function that outlived its budget (504) from infrastructure that was absent (503), attaches identifying x-hypercore-* thes to every response, and records deployment and invocation state machines as plaintext statuses that make every log line attributable.

II. Background and Related Work

This section fixes the technical substrate that the design assumes, then positions Hypercore against the managed platforms, volunteer-computing systems and research prototypes it must be read against.

A. Managed serverless computing

Commercial FaaS platforms expose functions through HTTPS endpoints with provider-managed autoscaling, cold-start pools and per-invocation billing [1–3]. Their design assumes a large, elastic provider fleet. Hypercore keeps the external contract — a function has a stable HTTPS URL — but replaces the fleet with participant machines, and therefore must push two responsibilities that providers normally own, namely code execution and reachability, onto the edge.

B. WebAssembly and WASI

WebAssembly (Wasm) [4] is a portable binary instruction format with a linear memory model, statically validated before execution: no instruction may address memory outside its module's bounds. Execution is sequential and deterministic given identical inputs and fuel settings, which makes resource accounting tractable. The WebAssembly System Interface (WASI) [5] standardises a minimal capability surface of file descriptors, clock, random values, and standard input/output, so that a module can perform I/O without filesystem or network authority unless granted. Wasmtime [6] is a production Cranelift-based runtime exposing consume_fuel, deterministic instruction budgeting, and epoch_interruption, cooperative deadline checks. Hypercore composes these two primitives into its termination guarantee in Section VI.

C. Compiling JavaScript to Wasm

A Wasm module cannot consume JavaScript source directly. Javy [7] resolves the mismatch by compiling an embedded JavaScript engine, QuickJS, itself to a Wasm ahead-of-time image and attaching the user's source as module data; instantiating the module boots the interpreter and runs the source. The result is a single worker.wasm file with no runtime dependency on Node or a browser at execution time. The cost is a compile step that becomes a deploy-time concern, paid once per deploy rather than per call, and quantified in Table XX.

D. Server-Sent Events

Server-Sent Events (SSE) [8] is a protocol in which a server holds an HTTP response open and pushes newline-delimited frames. Hypercore exploits the simplest valid subset: a stream is opened by one endlessly awaited GET request, events are named one-line JSON payloads, and keep-alives are comment lines that proxies ignore as data. Section VII-B gives the exact frame grammar; Section VII-C derives the delivery semantics that follow from it.

E. Why not containers?

An obvious alternative execution substrate is a per-function container or microVM [9,10]. Containers can support heavyweight runtimes, long-lived services and network access, but they demand root privileges for image lifecycle management, gigabytes of toolchain on every node, minutes-long image pulls on residential links, and an operator-grade patching story on machines that participants administer casually. A Wasm module is a 10–50 MB file, validated before execution, with a first-class instruction budget. For pure, stateless compute functions the trade favours Wasm decisively; Section XVI revisits what this choice excludes.

F. Isolation mechanisms on participant hardware

The freshness of the sandbox claim deserves a finer lens, because "isolation" names at least four implementable mechanisms that a participant machine could realistically host, spanning very different cost profiles for the joiner. Table I contrasts them on the five properties that matter for a donated fleet: privilege needed at install, startup cost per invocation, deterministic termination, permissions surface, and image weight. Processes and containers pay in privilege and patching; V8 isolates pay in the language assumptions they import (JavaScript semantics, bundled API); Wasm pays in input expressiveness (the module consumes bytes and produces bytes, and little else). Since the donated-fleet requirement includes residential Windows machines with consumer-grade antivirus, only zero-install-privilege, validated-answer options were contenders; of those, Wasm is the only practical one whose toolchain the agent can serve complete.

G. SSE protocol details that matter

Because the whole message plane rests on SSE, its constraining details belong in the background. An SSE session is an ordinary HTTP response with Content-Type: text/event-stream, kept open indefinitely; the server writes frames whenever it likes, and the browser/client library reassembles lines. Four protocol properties shape the design. (a) SSE is unidirectional: server to client; commands out of the node would need a second channel or a change of protocol, and the design has no such commands (Q4). (b) Automatic reconnection is built into user agents but must be disabled by hand here: the agent implements its own backoff, because a naive honouring of the protocol's default retry: hint would reconnect instantly in crash storms, the one situation where restraint is required. (c) Frames are delimited by blank lines, which makes partial writes harmless but makes interleaved large payloads impossible without framing discipline — hence event payloads are single JSON objects and large data moves out of band through the object store. (d) Intermediaries (proxies, hotel NATs, antivirus TLS inspection) buffer or kill idle streams unpredictably, which is why the heartbeat is 25 seconds rather than the "reasonable" 60, and why the reconnect trigger fires on both socket error and heartbeat silence rather than only on clean closure. These details are implementation folklore in most write-ups; here they are contract, because Section VII's properties cite them directly.

H. Wasm as a deployment format

Three Wasm properties matter for a deployment format rather than an execution substrate. Portable by design: the artifact is a binary that unloads identity of the producing machine — the same artifact executes identically on any participating operating system, so the object store's copy is of a format, not a build for a target; a heterogeneous fleet can share one artifact per deployment, which is what makes the fallback dispatcher of Section VIII-B meaningful at all. Versioned by content: a Wasm binary validates or it does not; validation happens at load, and the engine refuses anything else, so a truncated or corrupted artifact fails loudly on the executing node rather than subtly on a remote caller. Bounded: the format's execution semantics include the instruction stream itself, which is what makes fuel accounting possible at all — a container contract has no comparable handle. What Wasm does not give, and what the rest of the paper works around, is an ecosystem: no package manager targeting user source code as a Wasm module, no debugging toolchain at the level JS developers expect, no linters marking API that is absent inside the sandbox. The deployment format therefore carries a cultural cost for authors, which the starter template of the upload route partially absorbs, and which Section XVI-D prices honestly.

I. Managed FaaS and edge platforms

AWS Lambda [1] popularised event-driven function execution; Google Cloud Functions [2] and Azure Functions follow the same model. Cloudflare Workers [3] executes on V8 isolates at CDN points of presence and brought Wasm to serverless. Commercial worker runtimes target the same compute shape as Hypercore but retain provider-side fleets. Academic work on FaaS performance, cold starts and scheduling is surveyed in [11]. Hypercore differs in fleet ownership: execution capacity is participant-contributed, heterogeneous, and reached over persistent browser-grade connections rather than a managed cloud.

J. WebAssembly execution engines

The Wasm specification [4] and WASI [5] define the substrate; Wasmtime [6] and related runtimes implement it, with safety and performance profiles studied in [12,13]. Fuel-based determinism and epoch interruption are analysed for general embedding in [6]. Section VI adapts those mechanisms into a layered timeout contract for invocation deadlines.

K. JavaScript-on-Wasm toolchains

Javy [7] compiles a QuickJS-based runtime plus user source into one Wasm artifact; related approaches compile source to Wasm directly through LLVM-based toolchains or interpret JavaScript inside a Wasm-compiled V8. The two-stage esbuild then Javy chain used here is, to our knowledge, novel in one respect: the artifact is created per deployment on the executing node itself, so the control plane never runs user code and never hosts a build toolchain.

L. Volunteer and peer-to-peer compute

Volunteer computing systems such as BOINC [14] and desktop grids [15] historically targeted batch workloads with trusted binaries and checkpointing. Peer-to-peer serverless proposals [16,17] and academic edge-FaaS frameworks [18,19] route functions across heterogeneous nodes [20] but typically retain brokered transport (AMQP, MQTT, NATS) and credentials distributed to nodes. The previous broker-centred design of Hypercore (Section IV-B) showed the operational pain first-hand; the SSE design removes the broker, the inbound connectivity requirement, and node-held credentials simultaneously.

N. Broker-less and stream-based messaging

The design decision of moving from a broker to streams has precedents worth naming. Long-polling and Comet architectures [21] carried push semantics to browsers before SSE was standardised; today's server-push lane is dominated by SSE for unidirectional flows and WebSocket [22] for bidirectional ones. Webhook architectures push work by opening connections to workers, which requires reachable workers and re-introduces exactly the inbound-port constraint Hypercore refuses. Distributed-job frameworks over NATS/GNATS-style subjects [23] preserve broker independence but assume broker deployment as their first operation; by contrast the stream-per-node model trades message persistence for connection state, an acceptable trade because every event in the grammar is either immediately actionable or deliberately dropped (Section VII-C). The durable-queue systems that inspired this paper's write-ahead proposals [24] show how to recover the lost persistence when future work needs it without abandoning the one-connection invariant.

O. Wasm toolchains and the js-to-wasm path

Compiling managed-language dialects to Wasm has two competing lineages. The AOT lineage compiles a language's whole standard library into the module — Rust through wasm-bindgen [25], Go via GoWasm which makes multi-megabyte modules and slow instantiation, but uncoupled semantics. The interpreter-embeds-A lineage, Javy [26] among them, freezes an interpreter as the module and ships user source as data, buying per-deployment bytes and startup at the price of an interpretive ceiling on throughput — the trade analysis of Section V-D. Academic studies of serverless-on-Wasm [27] documented both dimensions, and fast pathological startup numbers for Wasm sandboxing [28] underwrite our cold-start expectations. The esbuild-specific bundling step has no published latency benchmarks the authors accept; our stage-timing table (Table XX) is therefore a contribution to that sparse measurement record rather than a comparison.

P. Placement and scheduling on heterogeneous fleets

Placement is art wherever machines disagree. Follower-style schedulers pick the first free slot [29]; bin-packing and constraint formulations [30] optimise tighter; volunteer-computing systems historically preferred owner-initiated pull because volunteers dislike being pushed. Hypercore's current fallback (uniform random among online nodes) sits deliberately at the cheapest end of this spectrum, on the argument of Section VIII-C that outage coverage, not load optimality, is the first-order requirement; the placement literature's machinery is what full fleet scheduling (Section XVI-F) would import. Two results from the literature shape our expectations for that extension: heterogeneity-aware placement beats random by a large factor specifically under skew [30], and availability-aware placement — weighting by measured sojourn — matters more than load-aware placement in fleets with heavy churn [31], which is why our CTMC sojourn statistics (Section VIII-F) matter operationally and not merely for presentation.

Q. Isolation taxonomies

Runtime isolation research divides sandboxes by mechanism (process, container, language VM, software-fault isolation) and by authority (capabilities, namespaces, seccomp-class filters). Wasm's position — SFI-class isolation with a linear memory and an explicit import surface [2,32] — has been evaluated in adversarial settings [33] and deployed at CDN scale [34], so our reliance on it inherits a well-exercised threat record rather than inventing one. What participant fleets add is the host problem: the operator of the machine is an interested third party (their machine is doing the work), and the failure modes Section IX catalogue — identity games, stream attachment, config drift — have no analogue in datacentre isolation studies. Our contribution to that record is the systematic treatment of host-trust asymmetry rather than a new sandbox mechanism.

III. System Model and Notation

A. Components as processes

Hypercore comprises one control plane C, a set of execution nodes 𝒩={n1,…,nN}, a set of callers, and two passive stores: a relational database and an object store. Figure 1 shows the placement of all components in the three planes.

Control plane. The process C owns the durable relations D (users, sessions, registered machines, deployments, invocations) and the object store O (raw source files and built Wasm artifacts). It also owns two volatile maps that exist only in memory: the online-node set 𝒜(t)⊆𝒩 of nodes with one open stream at time t, and the pending-invocation map 𝒫(t) which maps each in-flight invocation identifier to a response waiter and deadline. All durability lives in D∪O; both volatile maps are intentionally lossy under restart, a choice analysed in Section VIII-D.

Node. A node ni is the agent process on a participant computer. It registers itself with a hardware profile hi of CPU frequency, memory, disk and operating system, opens its stream, and implements two event handlers named deploy and invoke. The agent holds no credentials: it cannot read the object store directly, only through the control plane, and its only persistent identity is a machine identifier stored on disk.

Invocation. An invocation of deployment d is a single call: request bytes in, result out, plus the audit record written to the invocations relation with HTTP outcome, exit code, duration and error text. A function's observable behaviour is therefore a pure function of the request bytes; one call can neither read nor write the state of another call.

B. Structural properties

Three properties of this model drive most of the later analysis:

1) Volatility is local to the control plane. Only liveness and in-flight call state are volatile; everything else is durable under restart. A control-plane restart destroys exactly the volatile part (Section VIII-D) and recovers the rest without reconciliation.

2) Node state is disposable. The agent keeps no authority over stored data. Its artifact cache is a pure cache: on a restart it re-downloads artifacts by key, so a node recovers locally and cheaply with no reconciliation with the control plane.

3) Delivery is replace-on-reconnect. When a node reconnects, the control plane drops any older stream for the same machine id before registering the new one. Each node therefore has at most one live channel at any instant, which yields at-most-once routing (Section VII-C): a given event is written into exactly one stream or none.

C. End-to-end latency decomposition

A caller-side invocation crosses six sequential stages: control-plane ingest, durable lookup, stream enqueue, sandbox execution, result callback, and response egress. D. Transport encoding overhead

Results travel from node to control plane as base64 text so that the callback survives every intermediary unharmed. For a payload of m bytes the encoded length is

an expansion of about a third. A 4 MB captured-output limit therefore implies a 5.33 MB base64 blob on the callback, which is why the invocation-result endpoint carries its own enlarged 10 MB body limit and why large outputs dominate the callback stage in the latency decomposition.

F. Standing assumptions

The analyses of Sections VII, VIII, X and XV rest on the following explicitly stated assumptions. When an experiment violates one of them, the affected closed form goes with it — this is deliberate, so that empirical divergence localises to an assumption rather than to unspecified mechanisms.

A1 (clock hierarchy). Every timeout in the system obeys Tagent<Tserver, i.e. the agent abandons a function strictly before the control plane abandons the caller (Section VII-E). Violations surface as 504 timeouts that carry no function outcome.

A2 (single live channel). For each machine id, at most one HTTP stream is registered at any instant (replace-on-reconnect, Section VII-C). This is enforced structurally by the in-memory connection map.

A3 (bounded sandbox). A Wasm module cannot read or write outside its linear memory, cannot exceed the fuel budget, and cannot exceed the epoch deadline. Enforced by module validation and backed by engine-level fuel accounting (Section VI).

A4 (storage authority). Only the control plane holds object-store credentials; every node fetch transits the control-plane proxy and is checked against the two deployment-scoped key prefixes (Sections IX-B, XIV-B).

A5 (eventual register). A deployment's durable record precedes its routing event; a build's acknowledgment precedes its URL activation (Section XII-B). Neither ordering is transactional across stores.

A6 (clean crash semantics). A control-plane crash destroys the in-memory liveness and pending maps and nothing durable. Durable values written before the crash are recoverable; those in flight at the worst instant may fall one atomic write behind.

A7 (Poisson crashes). For the availability mathematics, control-plane crashes follow a Poisson process of rate λc independent of invocation arrivals. Section XV-C extends the corresponding independence assumption to the node side with a beta-factor model.

A8 (stationary node alternation). Node online/offline alternation has stationary mean sojourns μf and μr over the study window. Sustained load tests verify this before the availability numbers are trusted.

G. Structural properties

Four properties, each derivable from the assumptions above, answer the questions a new contributor asks first. They are stated operationally: what the caller observes, not merely what internal state holds.

P1 (no silent execution path). Every invocation produces exactly one of the classified responses of Appendix A. Argument: the sandbox outcome space is closed over exit / trap / timeout / fuel; the relay maps each to an HTTP class (Appendix A) or a transport failure under A1/A6; nothing else can terminate the caller's response.

P2 (bounded per-call cost). A single invocation cannot exceed its memory budget, its fuel backstop, or its wall-clock deadline up to one epoch tick (Section VI). Argument: A3 plus fuel exhaustion semantics plus the output caps of Section VI-C.

P3 (attributable failure). Any function-observable failure names the mechanism that produced it (error text and headers of Section XIII-E) because the outcome classifier never degrades to a bare 500. Argument: the classifier of Algorithm 2 is total and the relay never collapses distinct outcomes; the failure taxonomy of Appendix A records every terminal status it emits as its own row.

P4 (registrable anywhere). A node can join by knowing only one HTTPS address. Argument: registration needs no inbound port or node-held credential (A4); the stream is outbound; the artifact path is proxied. This is the property the message plane exists to protect, and every alternative transport considered in Section IV-B had to be tested against it.

IV. Architecture

Hypercore separates responsibility into three planes with strictly bounded interactions. The separation is the load-bearing decision of the whole design: control logic that answers what exists can never block on work that answers run this code, so a pathological user function cannot degrade platform reliability. Figure 1 shows the complete placement of components.

A. Control plane

The control plane consists of a Next.js dashboard and an Express 5 API server backed by PostgreSQL and an S3-compatible object store (Cloudflare R2 in the reference implementation). It stores users, sessions, passkeys, function source and metadata, deployment records, invocation history, and the registry of known machines with their hardware profiles. The API is layered in four strata — shared infrastructure, routers, controllers, services — so that no service function touches HTTP state and no controller issues database queries directly. Two orderings in the request pipeline are load-bearing and documented here because they are easy to silently break:

1) Raw-body routes mount before the global JSON parser. The invocation routes forward the caller's body bytes straight through to the function as standard input; if body parsing ran first, the original bytes would be lost. Accordingly those routes are mounted before the global JSON parser and install their own raw-body parser.

2) Literal paths are declared before parameterised paths. Express matches routes in declaration order; a later file-proxy route would otherwise be captured by an earlier parameterised pattern that reads its name as a deployment identifier.

B. Design evolution: from broker to streams

An earlier revision of the message plane used a RabbitMQ exchange and a per-user work queue. The broker design had four operational costs that surfaced in practice: the installer had to carry a broker URL and credentials; nodes needed a working AMQP client library; work routed to a node whose connection had silently died had to be re-queued explicitly; and the broker became a second stateful service to monitor. Replacing the broker with per-node SSE streams eliminated all four at once: the only user-facing configuration input is a web address, the transport client is the HTTP stack the agent already has, and a dead stream is both detected and replaced by reconnect (Section VII-C). The cost is the one documented in Sections III-A and VIII-D: the control plane becomes the rendezvous point whose volatile memory holds liveness and pending results.

C. Execution plane anatomy

The execution plane is a Tauri 2 desktop application with a React window for the human operator and a Rust backend for machine work. The Rust backend owns the SSE stream, the build pipeline (Section V), and the Wasm executor (Section VI). The UI half can invoke only an allow-listed set of IPC commands; it can display machine diagnostics and log tails, but cannot by construction ask the host to perform arbitrary operations. D. Naming and lifecycle

A function moves through three stages. In the write stage the author uploads TypeScript files plus a package manifest; the control plane stores them and records metadata without building anything. In the deploy stage the author selects a target node; a deployment record is created and a deployment event is written down that node's connection; the agent downloads sources, builds the Wasm artifact, uploads it, and acknowledges completion. In the invoke stage the built artifact is reachable at two URLs: an immutable deployment URL that always runs exactly one build, and a stable worker URL that always resolves to the most recently built deployment, which is the address normally shared. E. Storage and authority layout

Object keys are partitioned by deployment identifier: raw sources under one prefix, built artifacts under another, and every read or write passes through the control plane. The control plane enforces a prefix allow-list (rejecting any key outside the deployment-scoped namespaces), sanitises every uploaded file name to a bare basename to prevent traversal, and restricts uploads by extension to TypeScript files, the package manifest, and lock files. The consequence is an authority invariant: only the control plane holds storage credentials, so a compromised node can touch only data addressed to it, and a leaked dashboard session grants no access to node artifacts beyond what its user can already see.

V. The TypeScript-to-Wasm Compilation Pipeline

When a deployment event arrives, the agent executes a five-stage pipeline, shown in Algorithm 1 and Fig. 2. The stages are deliberately separated so that a failure is attributable to exactly one stage, and the failure semantics of adjacent stages differ by design.

Stage 1 (download). Source files are fetched with one HTTP request per file through the control plane, which proxies them from the object store. The agent holds no storage credentials whatsoever; a compromised node can read only the deployment currently addressed to it. A missing entrypoint after download is a hard failure of the deploy.

Stage 2 (bundle). The entrypoint and its imports are bundled into a single JavaScript file with esbuild. The agent probes a fallback chain of bundler candidates: a copy of esbuild shipped inside the installer, an esbuild binary on the PATH, an esbuild fetched through a package runner, and finally the Bun build command. If every bundler is unavailable, the raw TypeScript file is copied as the bundle input; this does not fail the deployment, because Javy may still compile plain JavaScript, and a missing bundler is visible on the node's toolchain status panel rather than hidden behind a silent substitution. G. Determinism and reproducibility of builds

A statistical detail with operational consequences: bundling is intended to be deterministic for identical inputs, so that a re-build after a harness upgrade produces byte-identical artifacts and cache-invalidation logic can hash-compare rather than re-deploy. Three factors undermine byte-identity in practice: tool version drift (esbuild and Javy are pinned but the fallback chain of Table VII can select different tools across machines), dependency resolution (package manifests can float), and source-set ordering in archive generation (unordered dict iteration in the manifest assembly can permute file order, which some bundlers fold in). The reference implementation pins the first and fixes the third with sort-before-hash; the second is the only residual, kept visible by hashing each artifact at build time and recording the hash in the deployment row. Where byte-identity matters — staged rollouts, cache-targeted debugging — the reproducer recipe is: same agent toolchain snapshot, frozen manifests, and the hash recorded before invocation traffic begins. Future work lists full reproducible-build certification, which matters more to fleet operators than to researchers but whose absence is cheap to document now rather than explain after the incident.

A. Deterministic instruction budget (fuel)

Wasmtime's fuel mechanism charges every executed instruction; when the budget is exhausted, execution stops deterministically. Hypercore sets the budget at Fmax=2×109 instructions per invocation. Fuel provides the machine-independent half of the termination guarantee:

B. Wall-clock deadline via epoch interruption

Each invocation carries a deadline. A helper thread sleeps for the remaining budget and then triggers Wasm's epoch-based interruption: the engine continues only at quantised checkpoints, and when the deadline epoch passed, the running instance halts at its next checkpoint and the call is abandoned. Epoch interruption is preferable to thread termination for two reasons: the host can still drain whatever output the function produced before the deadline, and the host process remains sound because user code never runs on the host's own threads. Combined with fuel, no invocation can exceed its deadline except by one checkpoint epoch, whose duration is bounded by engine constants and negligible at second-scale deadlines.

C. Output capping

Captured standard output is bounded at 4 MB and standard error at 64 KB, so a function that prints forever cannot fill the node's disk. The cap converts a potentially unbounded stream into a bounded one and makes the callback size predictable (Section III-D): at most 5.33 MB of base64 on the wire.

E. What the sandbox cannot protect

The sandbox answers what may the code do, not which code gets run. Deployment source reaches the node only through the control-plane proxy (Section V), and the build happens on the node with the toolchain the installer shipped. Two residual risks follow. First, an attacker able to substitute a toolchain binary on a node could in principle produce a malicious-looking but still validating module; the mitigations are toolchain integrity at install time and the rule that a Javy failure is fatal (no unverifiable artifacts are served), while a future extension may pin toolchain hashes per deployment. Second, resource-inducing side effects such as CPU contention between co-located functions on one node remain inherent to multi-tenant execution on participant machines; Section XVI discusses scheduler-level mitigations.

B. Reconnection and backoff

Because the stream is plain HTTP, any broker outage, network blip, laptop sleep or control-plane restart closes it and the agent reconnects. The reconnection delay doubles per attempt with a floor of 1 s and a cap of 30 s: the k-th attempt after a failure waits

Δk=min(b02k−1,Δmax)(8)
b0=1 s,  Δmax=30 s(9)

and the delay resets to b0 on the first success. The total waiting time within an outage of m consecutive failures is the truncated geometric series

S(m)=b0(2m−1)(10)

until the cap takes over; with p denoting the per-attempt success probability of a healthy server, the expected number of attempts until reconnect is

E[N]=1−pp(11)

An illustrative sweep: within about 2 s of an unplanned control-plane restart, healthy nodes have reconnected (observation in Section VIII-E) because the backoff was reset at the last success, so the first retry happens one second after the stream breaks.

C. Delivery semantics

Three properties hold of the message plane by construction, all following from replace-on-reconnect over a single in-memory map:

1) At most one live channel per node at any instant; hence at-most-once routing of each event: an event is written either into the unique live stream of its target or nowhere.

2) No queueing for offline nodes: a deployment targeted at a disconnected node is recorded with status offline and is not replayed when the node returns; the operator must re-deploy. This is a conscious trade: no durable broker means no queue backlog to audit, at the price of a manual retry.

3) A write is recommitted only for the newest connection; older ones receive nothing further, so duplicate delivery cannot linger in a dead socket.

The three properties can be stated once more as propositions with one-sentence arguments, which is the form a code reviewer can check against the router implementation directly.

Q1 (at-most-once delivery). Claim: an event targeted at node n is written into at most one live stream. Argument: under A2 there is at most one live stream for n; the router performs a single map lookup and a single write; the write either succeeds into that stream or the event is not delivered. Nothing in the data path can multiply a write.

Q2 (no phantom queue). Claim: an event targeted at a disconnected node is never delivered after reconnect. Argument: the event exists transiently inside a stream write, which is the only medium; no durable or in-memory queue exists behind the stream map. The deployment-status path instead records the omission as an explicit status.

Q3 (no zombie channel). Claim: after a reconnect, no event is written into the superseded stream. Argument: the map update removes the old registration before (or as) the new one installs; a lookup keyed by machine id can therefore only resolve to the newest connection. If the old socket were still half-alive at the transport level, its removal from the map ends its eligibility independently.

Q4 (command confinement). Claim: no event in the grammar (Section VII-A) can instruct an agent to execute outside the two sanctioned pipelines. Argument: the parser recognises exactly three names; unknown frames fail closed; both deployment and invoke handlers bind to pipelines with fixed inputs (Table IX and Algorithm 1), so there is no channel for an arbitrary command payload.

E. Layered timeouts

With a default invocation budget T=10s, the agent is instructed to abandon the function at

Tagent=max(1000ms,T−2000ms)(12)

while the control plane waits

Tserver=T+5000ms(13)

The ordering Tagent&lt;Tserver is deliberate: when a function is merely slow, the agent emits a specific timeout outcome first and the server relays it, so the caller receives a meaningful message; the extra five seconds of margin means callback latency cannot convert a real result into a bare timeout.

F. Worker-name collisions

The two-layer name check of Section III-E works as follows: the dashboard tries up to eight random candidate names first (returning the first free one even when the checks fail narrowly, deferring judgment to the definitive server-side check). Combining Eq. (4) with the eight-slot strategy, the residual probability that an upload conflicts with a name taken while the dashboard checked is bounded by the probability that a conflicting deploy interlaces within one upload window; the server-side unique constraint converts any residual conflict into a definitive HTTP 409 with a friendly message rather than silent corruption.

G. A queueing view of the relay

The components of the invocation decision of Section VII-D can be re-read as a queueing problem, which makes the caller-visible latency tractable before any measurement is taken. Three stages compete for the caller's attention: the control plane's own service (database lookup and record at rate μa), the stream write (negligible, modelled at rate μs), and the sandbox wait Wsb, which is the dominant term because it contains the entire function runtime. In series the mean caller-visible relay time is approximately

Wrelay≈1μa−λin+Wsb(14)

where λin is the arrival rate seen by one control plane — the whole fleet's rate in the single-server configuration, which is precisely why the analysis of Section X-B concentrates on ρcp=λin/μa for the control plane rather than on node-side saturation. Three consequences structure both the design and the evaluation. First, the stages are additive up to waiting; instrumenting the caller-visible stages separately (Section XI-D) validates additivity or exposes correlation, which no amount of end-to-end measurement alone can distinguish. Second, the sandbox wait is carried by the executing node, not by the fleet: a heterogeneous fleet produces a mixture over node weights, and the evaluation reports the mixture's moments rather than any single machine's. Third, Little's law bounds the pending population at λinWrelay callers, so the number of callers hurt by a control-plane crash is proportional to arrival rate times relay time — a prediction the crash-recovery metrics of Table XXII can test directly, and the reason campaign RQ4 treats the crash window as a measured quantity rather than an anecdote.

VIII. Reliability and Crash Consistency

A. Node availability

A node spends its life alternating between online (stream open) and offline (stream broken). Let μf be the mean time between node departures and μr the mean repair (reconnect) time after a departure. The long-run availability of one node is

A=μfμf+μr(15)

Departures concentrate on laptop sleep, network changes, and machine shutdowns; repairs are dominated by the reconnection loop of Section VII-B, whose expected delay from a healthy state is about two seconds. The control plane's view of availability is therefore typically optimistic: a portable machine offline at the couch returns in seconds.

B. Fleet availability

An invocation reaches its owner node first, and the implementation augments this with a fallback dispatcher: when the owner has no live stream, the server selects among the other online nodes and retargets the call to one of them, which pulls the artifact from the object store on a cache miss and reports the substitution in the response headers. If all of N nodes are offline simultaneously, no delivery is possible; the probability of that state is (1−A)N, and the fleet availability is

Afleet=1−(1−A)N(16)

which falls rapidly: with per-node availability A=0.9 and only N=3 nodes, fleet availability already exceeds 0.999 — and this is now not a theoretical bound but the behaviour the fallback dispatcher produces in practice. Two qualifications remain. The fallback chooses a candidate without observing load, so a busy machine receives overflow calls as often as an idle one; and artifacts are not pre-replicated, so a fallback call pays the artifact re-download of Section III-D on its critical path. Load-aware scheduling and pre-replication are the natural extensions (Section XVI-F). Real fleets also correlate, because shared power, shared networks and shared geography create correlated outages, so the independent-failure assumption must still be read as a first-order model, extended in Section XV-C.

C. Crash loss of in-flight invocations

Control-plane crashes are the reliability sharp edge of the design. Let control-plane crashes follow a Poisson process of rate λc, and let S be an invocation's service time distribution. Given a crash at an arbitrary moment while a call of duration S is in flight, the probability that the crash lands inside that call's vulnerable window is

P(call lost)=1−e−λcS(17)

More useful operationally: over a steady arrival rate λ of invocations, the expected number of in-flight calls lost per crash equals the number of calls started during the mean remaining service time,

E[lost per crash]≈λE[S](18)

by Little's law applied over a unit crash window. With a mean service time of a few hundred milliseconds and a modest arrival rate, loss per crash is small; but the accounting is exact and the mechanism deterministic: lost calls return 504 to their callers after the server-wait margin, and their invocation rows remain running indefinitely.

D. The stuck rows

Because there is no reconciliation sweep, an invocation row interrupted by a control-plane death stays at running permanently unless a replica's poll settles it. The implementation already contains one cross-instance rendezvous here: every waiting request also polls the durable invocation row every 750 ms, so a caller whose agent's answer landed on another replica of the API finishes normally from the stored result. What this cannot fix is the crash in which the in-memory waiter and the row's terminal update are both lost — the caller receives 504 after the wait margin and the row remains running indefinitely, an auditor-visible residue rather than a silent divergence. Deployments, artifacts, and all invocations not in flight at the crash are fully durable, so restart recovery is graceful except for in-flight calls. A periodic sweep that ages out stale rows is one housekeeping query and is listed as future work (Section XVI-F).

E. Reconnection after control-plane crash

Empirically and structurally, when the control plane dies every node's stream closes within one second. Because the agent's backoff delay was reset at the last success, its next retry happens after b0=1s, so all healthy nodes reconverge within about two seconds of the restart, as the observation table in Section XI records. The invalidation is visible in two service-level side effects: every call in flight at crash time times out at the caller, and any deploy routed within the reconvergence window falls to status offline and must be re-triggered.

F. A CTMC model of node availability

The two-state lifetime of Section VIII-A can be read as a continuous-time Markov chain with states on and off, transition rate α (departures per unit of online time) and δ (repair completions per unit of offline time). From the standard two-state chain, the stationary distribution of the alternate gives the availability of one node as

A=δα+δ(19)

— the same μf/(μf+μr) of Section VIII-A with μf=1/α and μr=1/δ, but now with transient behaviour attached. Under a fleet of N independent nodes, the number of nodes online at a random instant follows the binomial lattice, and the stationary probability that exactly k of them are online is

πk=N!k!(N−k)!Ak(1−A)N−k(20)

which re-derives the fleet availability as the tail probability 1−π0 and, more usefully, gives the whole distribution needed for capacity planning: the probability that a fallback dispatcher has at least one but fewer than c candidates to choose from is ∑k=1c−1πk. Transient terms matter at fleet scale too: after a mass event (a campus power cut returning), the fleet climbs its lattice from k=0 at rate δ per returning node, so reconstruction takes roughly (1−A)/δ per node, and nodes stagger in over the backoff jitter instead of thundering simultaneously — an emergent property worth measuring in evaluation (RQ4), because a correlated all-at-once return is exactly when the control plane's queueing discipline (Section X-B) is most stressed.

H. Extended availability arithmetic

The fallback dispatcher of Section VIII-B changes more than one availability headline; it changes the distribution of who serves what. Write pown=A for the owner being live and pfb for the fallback machinery succeeding given the owner is dead (a candidate exists and accepts). Per-call service success — where the caller sees a 200 from someone — is

Pok=A+(1−A)pfb(21)
pfb=1−(1−A)N−1(22)

so total caller-visible availability exceeds fleet availability whenever the fallback succeeds partly. What the caller gives up is where: with probability (1−A)pfb the answer comes from a foreign machine, paying the cold artifact re-download of Section III-D. The expected extra per-call time attributable to fallback is then

E[tfb]=(1−A)pfbtart(23)

with Sart the artifact size and Bup the owner's download rate for foreign artifacts — the relevant bottleneck is the store's relay through the control plane, so Bup is bounded above by the control-plane proxy's throughput. Substituting the reference values of Section XI: A=0.95, N=5, Sart=25 MB and Bup=50Mbps gives pfb≈0.998 and E[tfb]≈0.05×4s≈0.2s — a 200 ms average tax per call made up of rare 4-second events, which is precisely the shape the evaluation's per-call histogram must reproduce (a bulk near zero with a thin fallback tail), rather than a uniform slowdown. Expected fallback frequency also calibrates the operator experience: at fleet-average A=0.95 roughly 5 per cent of calls to a deployment are answered by a machine other than the owner, which is why the substitution headers of Section XIII-E are load-bearing for debugging rather than an audit nicety.

B. Authority invariant

The only component holding storage credentials is the control plane. A node reads bytes only by asking for a key under one of the two deployment-scoped prefixes; a key outside the allow-list is rejected before touching the store. Uploaded file types are restricted to TypeScript sources, the package manifest and lock files; every uploaded name is sanitised to a bare basename, defeating path traversal. Consequently a compromised node cannot read other tenants' buckets, and a compromised session cannot ask the object store for arbitrary keys.

C. Cross-origin surface

The agent's embedded browser reports a different origin per platform (a Windows WebView build reports one origin, macOS and Linux another, and development a third). An explicit allow-list enumerates all three, plus operator-configured origins, plus the dashboard origin, plus any loopback port, so a window arriving from a new platform is not silently blocked by its own browser. The allow-list is printed at server start for audibility. The security invariant that matters is credential locality: browser sessions authenticate only to the control plane, storage credentials never leave the control plane, and nodes authenticate by machine identity only.

X. Cost and Capacity Model

A. Monthly cost comparison

Under a commercial FaaS provider, a monthly invocation volume u with mean service time s¯ (seconds) at list price p per provisioned GB-second, plus a fixed platform expense c0, costs

Ccloud(u)=c0+pus¯(25)

Under Hypercore the same workload costs the operator the fixed development effort amortised (cdev), control-plane hosting ccp, and the participants' contributed machines, whose marginal cost is zero by agreement:

Chc(u)=cdev+ccp(26)

(the second term is independent of u because the control plane is a relay, not an executor). The break-even invocation volume at which participant computing beats the cloud baseline is therefore

u*=cdev+ccp−c0ps¯(27)

whenever ps¯&gt;0, i.e. Hypercore strictly dominates beyond any threshold once its fixed development cost is written off. Section XI evaluates that claim empirically rather than parametrically.

B. Control-plane capacity

Because the control plane only relays, its per-invocation work is a bounded amount of database lookup, stream write and callback resolution, modelled as an M/M/1 server at rate μ against an arrival rate λ. Stability requires ρ=λ/μ&lt;1, and the mean relay time is

W=1μ−λ(28)

Little's law (Nin=λW) then fixes the expected number of callers waiting on the control plane at any instant, which calibrates the pending-callers memory footprint used in the evaluation sizing.

C. Fleet capacity

Fleet throughput is bounded by the summed service rates of online nodes, Σ=∑iμi scaled by each node's own availability Ai:

Tfleet<∑i=1NAiμi(29)

Heterogeneity makes μi per-node; the participant fleet acts like a weighted pool of machines whose total capacity is additive when the dispatcher can place work freely. The current dispatcher sits between the two extremes: owner nodes take the normal path, and the fallback selector spreads calls that the owner cannot take uniformly at random over the remaining online nodes — so during single-node outages the effective bound is the surplus capacity of the online rest of the fleet, while steady-state routing still concentrates on the owner. Achieving the full additive bound in steady state requires load-aware placement, the natural extension (Section XVI-F).

D. Credential inventory

Every long-lived secret the system holds, who holds it, and what it unlocks, determines the blast radius of each compromise. XII. Operational Walkthrough

The preceding sections defined the architecture in the abstract. This section walks the same machinery through three concrete lifecycles, narrating every crossing of a plane boundary so that the reader can trace each of the guarantees claimed earlier to a particular step. The walkthrough uses a deliberately minimal worked function — a word-count service whose source is a single TypeScript file — because every generality of the design is easiest to audit when the payload is trivia; the interesting content is in the hops, not the computation.

A. Reference workload

The walkthrough function is:

Listing 1 — index.ts, the walkthrough workload
  1: async function main() {
  2:   const body = await Bun.stdin.text();      // request bytes
  3:   const words = body.match(/\S+/g) ?? [];
  4:   process.stdout.write(`${words.length}\n${body.length}`);
  5: }
  6: main();

The function reads the caller's bytes from standard input through the WASI standard-IO binding, computes two numbers, and emits them to standard output, which becomes the HTTP response body. It exercises exactly the interface of Table IX and nothing else, so its cost model is the pure overhead of the architecture: any latency it incurs on Hypercore beyond the sandbox itself is spend on ingest, relay and transport rather than on the workload.

B. A deployment from keystroke to live URL

The author writes the file in the dashboard editor, which issues an initial server-side name check against the check-name endpoint, then uploads the source in one POST carrying up to ten files. The control plane persists the files to the object store, writes the deployment row with status uploaded, and only then touches the message plane. Because the write precedes the route, a crash between the two leaves a deployment that exists and is built later, rather than an event with no durable record. This is why the evaluation plan measures the four stages separately: a slow Hypercore deployment could be blamed on three very different bottlenecks, and the fix differs accordingly.

Trace 1 (the 409 race) is the most confusing endpoint for a fresh reader because the deployment page says built while the invocation response claims the artifact is missing. The window is real and narrow: the agent's artifact upload and the first RSS read are sequential on the server but only eventual cross-plane, and the artifact key column is not yet set when the invoke read lands. The mitigations are the ones Section VII-F lists: the dashboard retries the eight-candidate name check, and the invoke path returns a specific 409 rather than silently proxying to nothing. Trace 2 (owner offline) proceeds along the fallback dispatcher rather than failing outright. The primary write into the owner's stream is attempted first; if the machine has no live stream, the server shuffles the remaining online nodes and retargets the invocation to the first that accepts it. The executing fallback node loads the artifact from the object store on a cache miss (no pre-replication exists), executes, and answers; the response then carries the substitution markers of Table XXXI so that the caller can see that execution happened somewhere other than the deployment's home machine. Only when no node at all is online does the caller receive a 503, accompanied by the candidate count that was attempted. Deployment routing, by contrast, still fails visibly: routing a build to an offline owner leaves the deployment live-but-unbuilt at status offline, because builds are owner-pinned and are not scheduled onto other nodes.

Trace 3 (control plane death) is the reliability story of Section VIII in miniature. Callers of in-flight calls first benefit from the durable-rendezvous poll: even a crashed and restarted API settles pending calls whose results were persisted by a replica or re-writable, because every waiter polls the invocation row. The calls that fall to 504 after the margin are precisely those whose waiter and row terminal update were both lost; their rows remain running, an explicit and documented residue — a housekeeping sweep is one query and is currently trade-off-deferred (future work).

Trace 4 (identity regeneration) is documented because it is the only path by which the fleet registry drifts from the truth. A stable machine identifier is derived at agent install and persisted; certain reinstallation or disk-wipe operations dissolve it, after which the same physical box registers as a new machine. The consequences are visible and easily pruned by an operator, and the failure catalogue treats it as an auditor-visible event rather than a silent aliasing.

F. Instrumented-state summary

Across the six traces, three system states absorb all the failure energy: the durable rows (always correct after settlement), the in-memory maps (resettable with visible symptoms), and the object store (never culpable, because everything is immutable-keyed and prefix-checked) — hence the paper's habit of seeking verification in exactly those places. Any future feature that introduces a fourth kind of state (distributed caches, replicated leases) inherits this appendix's obligation: add a trace, observe its risk envelope, and publish the failure mode alongside the benefit. The refinement this paper most wants is a crash-consistency test suite running the traces of Tables XXIV and N32 continuously, since traces fail rarely in the wild and continuous exercise is the only efficient way to observe regression. That suite is specified in Appendix D rows T28/T29 and is the first deliverable after the currently planned features.

The inventory of Table XXVIII is also an ordering contract. D. SSE wire format

The message plane speaks the smallest valid SSE dialect. Three named events exist; each frame is one event: line and a data: line carrying a single JSON object, followed by a blank line. A heartbeat is a comment line (a leading colon) and must be emitted even when no work flies, because idle streams die in unpredictable places — the reference server speaks every 25 seconds. Literally translated to text, three real frames look like:

event: connected
data: {"machineId":"a1f2…","online":true}

event: deployment
data: {"deploymentId":"b3c4…","entrypoint":"index.ts",
       "manifest":[{"name":"index.ts","key":"raw/b3c4…/index.ts",
                    "size":412}]}

event: invoke
data: {"invocationId":"d5e6…","method":"POST","path":"/",
       "query":"","body":""}

The parser is deliberately stateless between frames beyond two accumulators: the current event name and the buffer of data: lines. A malformed frame fails closed — it is skipped, and because every frame is a complete action, no partial frame can cause a partial side effect. The control-plane proxy accepts only keys under these two prefixes and rejects everything else before the object store is contacted — the prefix allow-list of Section IX-B in its implemented form. Denoting by nf the number of source files, the total object count generated per deployment is nf+1, and because sources rarely exceed a few files this bounds the byte-amplification of the upload path and justifies treating source traffic as a second-order term in the bandwidth analysis of Section XVI-B.

C. Identity stability

The primary key of the machines table deserves its own paragraph because three analyses rest on it. The agent derives a machine identifier from a stable OS-level unique identifier; if that is unavailable it persists a synthesised UID so that reinstallations of the agent on the same machine keep their identity. Registration is an upsert on this key, so reboots and reconnects are invisible at the registry level. The only known path to identity drift is full disk sanitisation or an OS- UID change — the duplicate-row edge of Section XVI-E — after which the same physical box appears twice until an operator prunes it. Everything else about identity is constrained from one side by this key: session tokens for agents do not exist, so the key is a coordination handle rather than an authentication credential, a distinction the security model of Section IX depends on.

XV. Extended Analysis

This section develops the analytic material of Sections VII-B, VIII, and X to closed forms that evaluation engineers can reuse directly. Each subsection isolates one mechanism, states its assumptions, and produces a quantity that the measurement plan of Section XI either validates or instigates a code change from.

A. Expected reconnection time under capped backoff

The reconnect loop of Section VII-B doubles its delay from b0 with a cap Δmax. Number the attempts after a failure k=1,2,…, write Δk=min(b02k−1,Δmax), let Ntry be the number of failed attempts before the first success (geometrically distributed with success probability p), and define the last uncapped index

E[Trec]=b0∑k=1K[2(1−p)]k−1+Δmax(1−p)Kp(37)

The two terms are diagnostic: the geometric sum covers the upswing until the cap engages, and the second term is the price of a persistent outage. B. Relay latency under general service times

Section X-B modelled the control plane as an M/M/1 server. The assumption is honest for the queueing skeleton but optimistic for the callback stage, whose duration inherits the residential uplink's heavy tail. The correct first correction is the Pollaczek–Khinchine expectation for an M/G/1 queue, which replaces Var of the service time in the wait term:

W=E[S]+λE[S2]2(1−ρ)(38)

with ρ=λ/μ. The two levers matter for capacity planning in opposite directions. Because E[S2] enters at second order, any heavy-tail stage dominates the queueing delay as load grows — so bounding the largest results (the 10 MB callback bodies) is more valuable than shaving the mean lookup, and it is why the reference implementation caps bodies rather than trusting the network. The Formulae also give the degradation law of the relay: near ρ→1 the queue delay diverges as (1−ρ)−1, and since E[S2] for a mixed callback population grows with the share of large outputs, the divergence is sharper than the exponential M/M/1 approximation suggests. Evaluation campaign RQ1 therefore reports p99 relay latency as the primary capacity signal, not the mean.

C. Correlated availability

The independence hypothesis behind the fleet-availability expression of Section VIII-B fails when whole fleets share fate: a power cut on one street, an outage concentrated on one ISP, or a synchronised laptop-sleep pattern across a campus all take several nodes offline at once. A standard first-order correction is the beta-factor model: split each node's unavailability into an independent part of mass 1−β and a common-mode part of mass β that removes all nodes together. The fleet then serves traffic with probability

Afleet=1−[β+(1−β)(1−A)N](39)

because independent breakdowns persist with probability 1−β — each failing with per-node odds 1−A — while the common-mode event succeeds in taking the fleet down with probability β. The equation's message is structural: the availability floor of the fleet is not zero but 1−β, so if the operator observes β=0.05 of correlated events, an intake of participants from a single neighbourhood caps the promise near 0.95 regardless of how many nodes join. Diversity of networks and census regions is therefore not an optimisation detail but the setting of the floor. Table XXXVI quantifies the effect.

D. Name-collision arrival rate

Section III-E computed the collision probability for u deployments; a server operator rather cares about the event rate. Let deployment creations arrive as a Poisson stream of rate λd per day and let the candidate space contain s names. A collision pair exists when two deployments created within one dashboard-check window w seconds draw the same name; under the birthday approximation the expected number of such pairs per day is

E[Cday]=λd22s(40)

for example, with λd measured in deployments per day at 100 per day and s=105 names drawn uniformly, the naive pair rate is 1002/(2×105)=0.05 pairs per day — and the effective rate is smaller still, because only creations interlacing within the w-second check window resolve. The server-side unique constraint then converts whatever residual stream manages to interlace into deterministic 409 responses rather than silent aliasing. The formulae turn the two-layer defence into a measurement question rather than an assumption: comparing creator logs against 409 logs over weeks of deployment traffic is one of the checked hypotheses of Section XI, since a 409 rate systematically above the point estimate would indicate that instance interlacing is wider than assumed.

E. Instruction rates to wall-clock

Equation (7) bounds execution by texec≤Fmax/rmin under the fleet-wide instruction rate. The rate is itself a random variable across heterogeneous participants. If lnr is approximately normal with mean mr and spread σr, and the fraction of nodes slower than the quantile is required below ϵ, the ϵ-slowest instruction rate is

rϵ=exp(mr−z1−ϵσr)(41)

and the corresponding planning bound on any invocation is texec≤Fmax/rϵ. With reference numbers mr=108 instructions per second and σr=0.7 on the natural-log scale (a hypothetical spread for a fleet of small consumer machines, to be tested against the census of Table XXXII at measurement time), the one-percent-slowest rate is roughly 1.9×107 instructions per second, so the fuel budget alone stops the tightest loop in under two minutes — usable as a backstop, wasteful as the primary mechanism. This is the quantitative reconciliation for why fuel is the backstop and epoch interruption the primary instrument: sweeping fuel on a slow node binds far later than the wall-clock deadline, so the epoch mechanism is what actually protects participant machines in the fast path.

F. Pending-set sizing

Little's law applied to the pending waiter map returns its resident count Lp=λtTsw, where λt is the tenant-total invocations per second and Tsw the caller-so-far wait. Each waiter holds a callback closure and a timer, an order wwaiter=103 bytes. The steady-state memory footprint of the pending set is then the product

Mp=λtTswwwaiter(42)

which grows linearly in all three factors. At ten calls per second with a mean wait of half a second, the set holds five entries — a handful of kilobytes, confirming that the pending map is not a memory hazard even under aggressive load tests. Its true risk is not size but durability (Section VIII-D), which is why every wall-clock analysis ends with the same caution: the map is cheap until it is irreplaceable.

XVI. Discussion and Limitations

A. Mostly-single-process control plane

The authoritative liveness map and the pending-invocation waiters live in one API process. The implementation already contains a partial answer for a load-balanced deployment: every waiter additionally polls the durable invocation row, so a callback that lands on a different replica still completes the caller's request, and results persisted by a replica are visible everywhere. What remains single-process is the authoritative set of in-flight deadlines: between two poll ticks a fast result is settled from memory, and a crash that loses both the waiter and the row update leaves a stuck row (Section VIII-D). A fully shared pending store or a lease-based queue closes that gap; both are standard machinery that the design deliberately did not adopt in its first revision, because a one-process invariant is easier to audit correctly than a distributed one. This remains the system's most significant scaling limitation, documented rather than hidden.

B. Bandwidth through the control plane

All source and artifact traffic is proxied through the control plane, which therefore becomes a bandwidth bottleneck for large bundles. Direct-to-storage signed URLs would relieve it but would reintroduce storage credentials on the agent. The reference implementation accepts the cost of relaying; measured implications appear as the wide gap between ingest and callback stages in Table XVIII.

C. Build-on-node

Requiring the node to compile code means the installer ships a working toolchain and first deployments pay the full build latency. In exchange, the control plane never executes untrusted code and never needs a cross-platform build harness of its own. A future build farm that reduces artifact sharing while keeping credential locality is an open design point.

D. Interface expressiveness

The stdin, environment-variable and stdout contract of Table IX is intentionally austere: functions can compute but cannot fetch, stream, listen, or call other functions. This keeps the sandbox small and audit simple, but it restricts applications to pure computation, and it means an entire class of loop-shaped workloads (fetch-then-transform, fan-out aggregation) cannot be expressed today. Extending the interface without expanding trust is an open problem: each new capability granted to the sandbox widens the audit surface in Table XIII.

E. Known sharp edges

1) Invocation rows interrupted by a control-plane crash can stay at running with no waiter left to settle them (Section VIII-D); a periodic ageing sweep is implemented trivially and deferred. 2) Duplicate node identities can appear after a hardware-identifier change regenerates a machine id; the registry then contains two rows for one physical machine. 3) A 409 still-compiling response after a successful deploy is the most confusing failure in practice: it is correct (the artifact upload may have raced the first invocation) but the message exists only because the agent-side build is asynchronous to the record status. 4) Steady-state execution routes always prefer the owner node, so a deployment whose owner is a weak box and receives heavy traffic cannot spread its load; the fallback selection covers outages, not saturation. Each of these is visible in logs and diagnosable by status; none is silent.

F. Future work

1) Fleet scheduling. Generalise the fallback selection into full placement: route steady-state calls across a chosen node set rather than to a single owner, reintroducing the pooled capacity bound of Section X-C; the open problem is placement under heterogeneous, changing availability and unreplicated artifacts. 2) Durable in-flight state. Move pending waiters to a small write-ahead log so a control-plane restart can replay them, eliminating the stuck-row class. 3) Streaming responses. Let the sandbox write increments to the caller through the stream rather than after completion, so long-running functions can return partial progress. 4) Interface growth. Grant narrowly-scoped capabilities (e.g., an HTTP fetch with an allow-list) so the workload class of Section XVI-D becomes expressible. 5) Stuck-row sweep. One housekeeping query; excluded only because it needs a control-plane lease to fight crash storms. 6) Artifact pre-replication. Warm one replica copy on a second node at deploy time so the first fallback call does not pay the full re-download.

H. Multi-region operation

The current design is single-control-plane, therefore single-region: every stream, every lookup and every relay passes through one datacentre. Geographically distant fleets are workable (a stream through a continent-scale tunnel behaves like any other stream) but the latency budget of Section III-C accumulates the control-plane round-trip for both ingest and callback, so a participant in another continent adds the same fixed cost twice. Multi-region deployment has a clean seam, because the planes partition: each region can run a complete control-plane replica with its own stream map, database and object store, and invocations route to the region hosting the deployment's owner. What does not partition automatically is addressing — worker URLs are names, not region-bound identifiers, so a global name layer (DNS-level or anycast) is required above the regional control planes, and the durable invocation rows become per-region with the operator's choice of replication or federation for the history view. The honest assessment is that multi-region is an integration project, not a redesign: Sections III–VII contain nothing that assumes co-location, but Sections XI and XIII assume it throughout, and every latency number in the evaluation would need per-region granularity rather than a single vantage point. That is why the limitation is stated here rather than fixed in code: the measurement commitments are to single-region behaviour first, and claiming regional numbers without redoing the decomposition would be exactly the kind of quiet scope-shrink this paper tries to make impossible.

I. Observability

The system is deliberately telemetry-free: all durable state is queryable rows, and operators debug from those rows plus the API and agent logs. This section records what that gives and what it costs. It gives an audit path — any invocation's lifecycle is reconstructible from its row (status, duration, executor, owner, error) and the transcript format of Appendix E combined with the logs makes every plane crossing attributable; it costs that nothing is measured continuously, so availability statistics of Section VIII must be computed by an operator's queries over collected logs rather than read from a dashboard, and drift detection (a degrading node class, a rising 409 rate) is whoever's recurring job. The design trade is defensible for a research system where measurement campaigns are deliberate events (Section XI), but the productionisation path needs a minimal metrics lane — counters exported per plane, no payload contents — and that lane is specified as future work so that it does not sneak in as per-node logging after an incident. What we will not do for observation's sake is weaken P3 (attributable failure): any metric that blurs outcome classes to make dashboards prettier trades the system's audit story for cosmetics.

J. Billing and fair division

If the platform ever charges, three design facts change. The cost model of Section X prices Hypercore by avoided cloud spend, not by chargeable usage, so a billing system would need usage attribution at invocation granularity — the rows carry worker and machine identity, so attribution is mechanical. Fair division across participants is harder: nodes that take more invocations burn more electricity for other people's code, and the fallback dispatcher randomly concentrates overflow onto whichever nodes happen to be online, so naive pay-per-execution would reward mere uptime rather than useful service. The accounting-based remediation is simple (weight fallback choice inversely to each node's recent execution count, costless and trust-free) and is listed with the scheduler work in Section XVI-F. What we decline to design here is the trust layer: charging participants for electricity without becoming their employer's payroll system is a product question with legal surface area the paper's scope does not open, exactly the boundary the architecture's no-financial-relationship stance (Section I) was drawn to protect.

XVII. Conclusion

Hypercore demonstrates that a distributed, participant-owned execution plane for TypeScript functions can be operated safely with remarkably little machinery, provided that user code is compiled to WebAssembly and executed under WASI with hard fuel and clock limits, routing is stitched with one persistent outbound connection per node rather than a distributed message broker, and the control plane is explicit about what it can and cannot guarantee durably. The system achieves NAT traversal without configuration, credential-free participation without leaking storage keys to nodes, and deterministic termination of adversarial functions; its refusal to hide trade-offs makes every failure mode attributable from logs alone. The evaluation plan of Section XI is designed to quantify where the architecture wins (zero-cost marginal compute, honest failure buckets) and where it loses (callback latency through the control plane, single-process liveness). The broader claim is methodological: a distributed runtime can be made safe by making trust boundaries narrow and visible—one stream per node, one artifact per deployment, one callback per call—rather than by adding brokers whose distributed invariants are harder to reason about than the code they coordinate.

Appendix F — Operational runbook

This appendix collects the operator procedures that the analysis assumed exist somewhere. They are written against the reference deployment (one API server, one PostgreSQL, one object store, an arbitrary participant fleet) and should be executed in the order shown when standing up a fleet for measurement.

A. Standing up a measurement fleet

1) Provision the control plane: PostgreSQL with the migrations applied, the object store with the two key prefixes created, and the API server configured with the connection strings, T budget, and the cross-origin allow-list from Table XXIX. 2) Verify the liveness endpoint returns the greeting JSON and that the CORS line printed at start matches the expected set before any agent exists. 3) Install the agent on each participant machine from the signed installer; the installer embeds the control-plane URL and no other configuration. 4) Confirm each machine appears in /api/v1/nodes with its hardware census (Table XXXII) and holds one open stream in /agents/online. 5) Deploy the walkthrough function of Section XII to exactly one machine and invoke it twice: the first response measures the warm path, a restarted-agent second machine measures the re-download path. 6) Run the adversarial trio (Table XXI) once against the fleet to confirm fuel, deadline and cap configuration before measurement traffic begins.

B. Post-crash checklist

After an ungraceful control-plane exit:

1) Confirm agents reconnect autonomously within the backoff bound (Section XV-A predicts ≈1–2 s fleet-wide); if any machine is absent after 30 s, check its local clock and TLS chain before suspecting the network. 2) Query invocations for rows left running; these are the loss accounting of Section VIII-D and should be annotated with the crash timestamp. 3) Record callers' 504 counts and any 409 responses observed during the reconvergence window (Section VIII-E). 4) Then patch the age-out sweep as noted in Section XVI-E, or delete stale rows by hand if the sweep option is still deferred. 5) No other recovery action exists: deployments and artifacts are durable by construction.

B. Expected results as predictions

Pre-registering expectations converts the campaign from exploration to test. In scenario S1, the additive decomposition of Section III-C must hold within the mix tolerance, or the per-stage instrumentation is mis-attributing. In S2, per-node ρi must stay below 1 well before the load generator notices, because the fleet's M/M/1 bottleneck is the control plane, not any node — if a node saturates first, the census weights underestimate its slowness. In S3, the p99 collision pattern must show the queue divergence of Section XV-B, meaning the run nearest ρcp=1 is the campaign's single most informative sample. In S5, the loss ratio must scale with λW, and its slope is the number the crash-recovery story hangs on; a systematic deviation there would falsify A6's clean-crash assumption, which is documented in this paper rather than assumed quietly. These predictions are written before the fleet is recruited; they make the final tables enforceable commitments instead of narrative decoration.
